# 百度识图「以图搜图」爬虫：老方案为什么失效，新方案为什么能过

> 一篇带实测数据的对比复盘。两种实现都跑过同一批接口，用返回码而不是"感觉"来说明问题出在哪一层。

## 一、背景

图库类项目里，「以图搜图」是个很讨喜的功能：点一张图，找出相似的图片。

实现路线无非两条：

1. **官方 API**：稳定、有 SLA，但要申请、要付费；
2. **爬虫**：免费、零门槛，代价是**接口随时会变**，而且失败时的报错往往极具误导性。

本文讨论第二条。之所以值得写一篇对比，是因为网上流传的两套代码**看起来只是写法不同，实际是两条完全不同的通道**，风控待遇天差地别——很多人卡在第一步，却一直以为是自己的参数写错了。

两套实现分别是：

- **老方案（URL 代抓）**：教程/原版项目的写法，三步：`upload(image=图片URL)` → 解析 HTML 拿 `firstUrl` → 请求 `firstUrl` 拿 `data.list`；
- **新方案（文件上传）**：移植自 Python 项目 [PicImageSearch](https://github.com/kitUIN/PicImageSearch)，四步：`multipart` 上传图片字节 → 解析结果页 HTML 里的 `window.cardData` → 解析 `same`/`simipic` 卡片 → 对 `simipic.firstUrl` 二次请求拿列表。

## 二、两种方案的流程

### 老方案：URL 代抓，三步

```
POST https://graph.baidu.com/upload?uptime=<毫秒时间戳>     Content-Type: form-urlencoded
     image=<图片URL>&tn=pc&from=pc&image_source=PC_UPLOAD_URL
        │  响应 {"status":0,"data":{"url":"https://graph.baidu.com/s?..."}}
        ▼
GET  https://graph.baidu.com/s?...
        │  从 <script> 里正则抠出 "firstUrl":"..."
        ▼
GET  https://graph.baidu.com/ajax/pcsimi?...&session_id=&sign=&tk=
        │  响应 {"status":0,"data":{"length":30,"list":[...]}}
        ▼
     data.list  →  缩略图 thumbUrl + 来源页 fromUrl
```

核心代码（三步各自的入口）：

```java
// Step 1：把图片 URL 丢给百度，让百度自己去抓
Map<String, Object> formData = new HashMap<>();
formData.put("image", imageUrl);          // ← 注意：这里是一个 URL 字符串
formData.put("tn", "pc");
formData.put("from", "pc");
formData.put("image_source", "PC_UPLOAD_URL");
String url = "https://graph.baidu.com/upload?uptime=" + System.currentTimeMillis();
HttpResponse response = HttpRequest.post(url).form(formData).timeout(5000).execute();
// ... 取 data.url，URLUtil.decode 后返回
```

```java
// Step 2：Jsoup 抓结果页，正则抠 firstUrl
Document document = Jsoup.connect(url).timeout(5000).get();
for (Element script : document.getElementsByTag("script")) {
    if (script.html().contains("\"firstUrl\"")) {
        Matcher matcher = Pattern.compile("\"firstUrl\"\\s*:\\s*\"(.*?)\"").matcher(script.html());
        if (matcher.find()) {
            return matcher.group(1).replace("\\/", "/");
        }
    }
}
```

```java
// Step 3：请求 firstUrl，拿图片列表
HttpResponse response = HttpUtil.createGet(url).execute();
// ... 解析 data.list，转成 ImageSearchResult
```

### 新方案：文件上传，四步

```
POST https://graph.baidu.com/upload                          Content-Type: multipart/form-data
     from=pc  +  image=<图片二进制, filename=image.jpg, image/jpeg>
     header: Acs-Token: ""
        │  响应 {"status":0,"data":{"url":"..."}}
        ▼
GET  结果页
        │  从 HTML 里提取 window.cardData（一个 JSON 数组）
        ▼
遍历卡片，按 cardName 分流：
     same     → tplData.list        同源/完全匹配
     simipic  → tplData.firstUrl ──┐ 相似图片，需要二次请求
     noresult → 直接结束           │
                                   ▼
                     GET firstUrl → {"data":{"list":[...]}}
```

关键代码：

```java
// 关键差异 1：请求体是 multipart，image 是"文件"而不是"URL"
String boundary = "---BaiduSearchBoundary" + System.currentTimeMillis();
addFormField(parts, boundary, "from", "pc");
addFilePart(parts, boundary, "image", "image.jpg", "image/jpeg", imageBytes);

HttpRequest request = HttpRequest.newBuilder()
        .uri(URI.create(UPLOAD_URL))
        .header("Content-Type", "multipart/form-data; boundary=" + boundary)
        .header("Acs-Token", "")            // 关键差异 2：模拟官方 SDK 的请求形态
        .POST(HttpRequest.BodyPublishers.ofByteArray(requestBody))
        .build();
```

```java
// 关键差异 3：不再正则抠 firstUrl，而是用状态机从 HTML 里切出 window.cardData
// （原因见第六节：正则处理不了嵌套数组和字符串转义）
int start = html.indexOf('[', html.indexOf("window.cardData"));
int balance = 0, end = -1;
boolean inString = false, escape = false;
for (int i = start; i < html.length(); i++) {
    char c = html.charAt(i);
    if (inString) {
        if (escape) escape = false;
        else if (c == '\\') escape = true;
        else if (c == '"') inString = false;
        continue;
    }
    if (c == '"') inString = true;
    else if (c == '[') balance++;
    else if (c == ']' && --balance == 0) { end = i + 1; break; }
}
// 再交给 Jackson 反序列化成 List<JsonNode>，按 cardName 分流
```

## 三、关键差异一览

| 维度 | 老方案（URL 代抓） | 新方案（文件上传） |
|---|---|---|
| `Content-Type` | `application/x-www-form-urlencoded` | `multipart/form-data` |
| `image` 参数 | **一个 URL 字符串** | **图片二进制**（`image.jpg` + `image/jpeg`） |
| 谁去取图 | **百度服务器自己去抓那个 URL** | 不用抓，图已在请求体里 |
| 对应网页入口 | "粘贴图片网址"（`PC_UPLOAD_URL`） | "选择本地文件" |
| 额外请求头 | 无 | `Acs-Token: ""`（官方 SDK 会带） |
| 结果提取方式 | 正则抠 `firstUrl` | 状态机切 `window.cardData`，按卡片类型分流 |
| 前置依赖 | 图片必须**公网可直链**且百度抓得到 | 无，任何字节流都行 |
| 失败面 | 参数校验 + 图片可抓取性 + 风控，三层 | 少一整层 |

## 四、实测：老方案到底死在哪一层

我把 `/upload` 和 `/ajax/pcsimi` 两个接口都打了一遍，下面是原始返回。

### 4.1 `/ajax/pcsimi`（第三步那个取列表的接口）

| 请求 | 返回 | 结论 |
|---|---|---|
| 不带任何参数 | **HTTP 400** 纯文本 `Bad Request` | 缺必需参数，网关层就拒了 |
| 教程里那条老 URL（参数齐全、早过期） | HTTP 200 + `{"status":400,"data":null}` | 参数齐全，是**凭证失效** |
| 去掉 `extUiData[isLogoShow]` | HTTP 200 + `status:400` | 非必需 |
| 去掉 `inspire` | HTTP 200 + `status:400` | 非必需 |
| 去掉 `limit` | HTTP 200 + `status:400` | 非必需 |
| **去掉 `next`** | **HTTP 400** | **必需参数** |
| **去掉 `render_type`** | **HTTP 400** | **必需参数** |
| `sign` 截断成 31 位 | **302 → `/errpage?pron=bff`**（"未找到相关结果"） | 签名格式非法 → 错误页 |
| `sign` 换成 32 位全 0 | HTTP 200 + `status:400` | 签名校验失败 |
| 某条真实 `firstUrl` | **302 → `/errpage?pron=bff`** | 签名能过，但会话已无结果 |

**这里最重要的一条经验**：同一个路径存在**两种完全不同的"400"**——

- **HTTP 400 + 纯文本**：参数/格式层被拒，通常是 URL 不完整、被截断，或必需参数缺失；
- **HTTP 200 + `{"status":400}`**：参数没问题，是 `session_id + sign + tk` 这套**一次性短时效凭证**失效了。

分不清这两者，就会一直在错的方向上改代码。

### 4.2 `/upload`（第一步那个上传接口）

| 请求 | 返回 |
|---|---|
| `image=某技术站 logo` | `{"status":1002,"msg":"Params illegal"}` |
| `image=百度自家 CDN 的图` | `{"status":1,"msg":"Reject"}` |
| 同上 + 浏览器头（UA / Referer / Origin / Accept / X-Requested-With） | `Reject` |
| 同上 + 浏览器头 + **真实百度 Cookie**（`BAIDUID`/`PSTM`/`BIDUPSID`/`BAIDUID_BFESS`） | `Reject` |
| `GET https://graph.baidu.com/`（桌面 UA） | **302 → `https://m.baidu.com`** |

从"只换图片就换错误码"可以读出：`1002` 这一档**在校验图片本身**能不能被受理（能否抓到 / 是否合规），这正是"代抓"通道的特征；而图片没问题之后，才轮到风控的 `Reject`。

### 4.3 三个结论

1. **不是"参数写错了"**。我把 `tn`/`from`/`image_source` 全删掉，返回码**一个都没变**（还是 `1002`）——说明缺参数不是原因；真正影响结果的是那张图。
2. **也不是"缺请求头"或"缺 Cookie"**。浏览器头补齐、真实百度 Cookie 带上，依然是 `Reject`。它拦的不是某个头，而是整个请求形态/指纹。
3. **教程里硬编码的测试 URL 早就失效了**。原版代码的 `main` 方法里写死了 `session_id=16250747570487381669&sign=1265...&tk=4caaa`，我实测这条返回的是 `{"status":400,"data":null}`。很多人第一次跑就报错，其实不是自己写错了——是那串凭证几年前就过期了。

## 五、机制分析：新方案为什么能过

按可能性排序：

**1. 消掉了"代抓"这一整层（最主要）**
老方案等于对百度说"你去 `https://…/logo.png` 把图拿下来"。于是百度必须真的抓到这张图、再判断合规性——这就是 `1002 "Params illegal"` 的来源，也是为什么换成百度自家图就变成 `Reject`（图没问题了，轮到风控）。新方案把图片字节直接塞进请求体，**这一层校验和失败点根本不存在**。

**2. 风控口径不同**
"代抓 URL"是被刷得最凶的通道（批量刷图、SSRF 类滥用都走这里），所以百度对非浏览器流量卡得最死。文件上传是网页正常路径，判定宽松得多。

**3. `Acs-Token` 头**
它是百度前端 SDK 上传时会带的一个 token 头。PicImageSearch 特意保留（空值），作用是让请求看起来像**官方 SDK 发出的**，而不是第三方脚本拼的。老方案一行头都没加，等于主动暴露"我是爬虫"。

**4. 附带好处：不要求图片公网可达**
老方案要求图片公网直链且百度抓取器能访问——私有读的对象存储、防盗链、内网地址、签名过期的临时链接全都会失败，而且报的还是误导性的 `1002`。新方案不关心图片来源，本地文件、私有桶里的图都行。

> **方法论提醒**：新方案一次性改了 4 个变量（上传通道、`Acs-Token`、`uptime`、`tn`/`image_source`），所以严格说"到底哪个变量是关键"只能排序、不能断言。想确认就做一次对照实验：`urlencoded + URL`（老）／`urlencoded + URL + Acs-Token`／`multipart + 字节 + Acs-Token`（新）／`multipart + 字节`（不带 Token），一次跑完看哪一格通。另外 `uptime` 基本可以忽略——我实测传一个很旧的固定时间戳，参数校验照样进行。

## 六、代码对照：三处最关键的差异

**1. 请求体**：老方案 `.form(formData)`，`image` 是字符串；新方案手工拼 multipart（boundary + `Content-Disposition` + 二进制段 + 结尾 `--boundary--`），`image` 是文件。

**2. 请求头**：新方案多了 `Acs-Token: ""`。

**3. 结果提取**：这是最容易被忽略、但决定"能不能解析出来"的一处。

老方案用一个正则从 `<script>` 里抠 `"firstUrl":"(.*?)"`。它能用，是因为 `firstUrl` 是一个**扁平的字符串字段**。

新方案要拿的是整个 `window.cardData`——一个**嵌套数组**，里面还有被转义的引号（例如 `imageUrl` 里带 `\/`、查询串里带 `%2F`）。正则遇到这种结构会出现：截断（贪婪/非贪婪都救不了嵌套）、或者被字符串里的 `]` 提前截断。所以新方案用了**状态机**：维护 `balance` 计数括号层级，同时用 `inString` / `escape` 两个标记跳过字符串内部的括号——这样无论嵌套多深、字符串里有多少转义，都能切出完整的 JSON 数组，再交给 Jackson 反序列化。

同理，卡片分流也要按类型判断，而不是只认一个字段：

```java
if ("noresult".equals(cardName)) { /* 无结果，直接结束 */ }
if ("same".equals(cardName))     { /* tplData.list → 同源/完全匹配 */ }
if ("simipic".equals(cardName))  { /* tplData.firstUrl → 二次请求拿相似图列表 */ }
```

## 七、工程化：别让爬虫拖垮主流程

爬虫代码写完只是开始，接入项目时建议做到这几点：

**1. 用门面模式隔离实现**
上层（Controller）只依赖"给一张图、返回相似图列表"这个能力，具体是百度还是别的服务，全部收在门面类里：

```java
public static List<ImageSearchResult> searchImage(String imageUrl) {
    ThrowUtils.throwIf(StrUtil.isBlank(imageUrl), ErrorCode.PARAMS_ERROR, "图片地址不能为空");
    BaiduResponse response;
    try {
        response = BaiduImageSearch.search(imageUrl);
    } catch (Exception e) {
        log.error("以图搜图失败，imageUrl={}", imageUrl, e);
        throw new BusinessException(ErrorCode.OPERATION_ERROR, "以图搜图失败，请稍后重试");
    }
    return convert(response);
}
```

以后换服务，Controller 一行都不用动。

**2. 区分"调用失败"和"没有结果"**
这两个语义必须分开，否则前端会把"被风控拦了"显示成"没有相似图片"。判据很简单：**结果页 URL 是否为空**——为空说明上传那一步就失败了，应当抛业务异常；不为空但没有列表，才是"真的没有相似图"。

**3. 留一个"字节重载"**
如果图片存在**私有读**的对象存储里，百度抓不到裸链，URL 那条路必然失败。所以门面里同时提供 `searchImage(byte[])`：先从存储把字节读出来再上传。这也是新方案最大的实际价值。

**4. 缓存 + 限流 + 权限（重要）**
- 这个接口每次调用都会真实打一次第三方，被刷的话**出口 IP 会进风控**，所以要限流、要考虑把结果缓存起来（同一张图短时间内没必要重复搜）；
- 接口别做成完全公开的，加个登录校验成本很低；
- 抓取要有节制：控制频率、失败不要无脑重试。

## 八、遗留问题与风险提示

- **老方案：已失效**。本文所有 `/upload` 与 `/pcsimi` 的返回码都是实测结果，证据在第四节。
- **新方案：机制上规避了上述三层失败点，且是社区在用的实现，但"接口随时会变"这件事对两种方案一视同仁**。本文不声称它永久有效；建议保留一个"搜图不可用时优雅降级"的开关。
- 两种方案的共同前提是：**搜索结果页的 HTML/JSON 结构**。一旦百度把 `window.cardData` 改名或换结构，解析就会静默返回空列表——这也是为什么"上传成功但结果为空"时，第一个要排查的是页面结构，而不是网络。
- **合规与频率**：这类抓取只适合学习与研究，注意不要给目标站点带来压力，也不要用于商业用途。

## 九、小结

| | 老方案 | 新方案 |
|---|---|---|
| 通道 | URL 代抓（百度替你取图） | 文件上传（图在请求体里） |
| 第一步能否通过 | ❌ 图片可抓取性 + 风控双重门槛，实测全 `Reject` | ✅ 少一层校验 |
| 结果提取 | 正则抠扁平字段 `firstUrl` | 状态机切嵌套 JSON `window.cardData` |
| 对图片存储的要求 | 必须公网可直链 | 无要求 |
| 工程建议 | 已不建议使用 | 配合门面 + 失败语义 + 缓存限流 |

一句话：**换的不是"写法"，是"通道"。** 老方案把取图的活儿外包给了对方服务器，于是要同时通过"图能不能被取到"和"你是不是浏览器"两道检查；新方案把图直接递过去，只剩下后者——而后者靠贴近官方 SDK 的请求形态（multipart + `Acs-Token`）来降低风险。
